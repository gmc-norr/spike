Development practice

  • Each change is pre-registered: a plan with locked pass criteria is committed first, then the code, then the result (supported, refuted or inconclusive)
  • A check is trusted only after it has been run against an input it must reject
  • Mutation testing: deliberately broken versions of new code must fail the test suite (all caught in each of the last four changes)
  • 754 automated tests; the measured numbers in the documentation were re-run against the current code in October 2026
  • Refuted changes are kept and logged rather than tuned until they pass

The method matters as much as the code. Pass criteria are committed before any data are seen, so a result cannot be bent to fit. New checks are tested against inputs they should reject, because a check that never fails proves nothing. The quality model in this talk is an example: its first rewrite was measured, failed two of its locked checks, and was logged as refuted; the second was built on what that failure showed.
